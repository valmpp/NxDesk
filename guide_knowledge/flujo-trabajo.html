06 · Flujo de trabajo y Git

Gestión de código, Rediseños e Incidentes

El código fuente es el activo más importante del proyecto. Este flujo garantiza que ningún cambio rompa producción y que todo commit tenga trazabilidad auditable según ISO 90003.

La regla de oro: La rama main es sagrada. Todo código que llega a main está validado, probado, aprobado por L3/QA y listo para salir a producción en cualquier momento. Cero tolerancia a commits directos en main.
01

Estrategia de ramas (Git Flow Adaptado)

Mantenemos un flujo estructurado pero ligero. Solo existen dos ramas estables; todo lo demás es efímero.

🌳 main

Espejo exacto de producción. Protegida por reglas estrictas. Solo acepta merges desde PRs validados o merges directos desde staging en momentos de release.

🛠️ staging (o develop)

El entorno de integración. Aquí se despliegan automáticamente los cambios para revisión de QA. Todo PR de feature apunta aquí primero.

🚀 feature/TICKET-ID

Para desarrollo de nuevas funcionalidades. Se crean a partir de staging. Ejemplo: feature/NX-102-login-oauth. Trazabilidad directa con ClickUp/Linear.

🐛 bugfix/ o hotfix/

bugfix/ sale de staging para errores en desarrollo. hotfix/ sale de main para emergencias en producción e incluye rollback de seguridad rápida.

02

Convención de Commits

Aplicamos Conventional Commits. Esto nos permite generar Changelogs automáticos y entender el historial sin leer el código.

⚠️
Importante: Todo commit debe contener el ID del ticket para cumplir con el estándar de trazabilidad. Ejemplo: feat(auth): [NX-102] agregar validación de JWT.
PrefijoCuándo usarloEjemplo
feat:Una nueva funcionalidad en el sistema.feat(orders): [NX-150] endpoint para cancelar orden
fix:Corrección de un bug.fix(auth): [NX-151] error de expiración en refresh token
docs:Cambios que solo afectan a docs/.docs(adr): [NX-152] agregar ADR-004 sobre Redis
refactor:Cambio de código que no corrige un bug ni añade feature.refactor(core): [NX-153] extraer lógica de rate limiting
test:Añadir o corregir pruebas unitarias / e2e.test(orders): [NX-154] tests para transición de estado
chore:Actualización de dependencias, scripts o CI/CD.chore(ci): [NX-155] actualizar pipeline de docker
03

Ciclo de vida del Pull Request (PR)

1
Creación y descripción del PR
El PR debe tener contexto. ¿Qué problema resuelve? ¿Cómo se probó? Si afecta UI, debe incluir capturas de pantalla. Si cambia infraestructura, debe notificar al equipo.
Autónomo
2
Checks automáticos (CI)
El pipeline compila el proyecto y ejecuta los tests. Luego, SonarQube escanea el código. El PR se bloquea si hay fallos en los tests o vulnerabilities/bugs críticos.
Automático
3
Code Review (Peer Review)
Obligatorio mínimo 1 aprobación de un L2 o L3. El enfoque del revisor no es solo buscar errores, sino evaluar la arquitectura, legibilidad y alineación con las reglas de negocio.
ISO 90003
4
Aprobación de QA en Staging
Una vez mergeado a staging, el entorno se actualiza automáticamente. QA valida el flujo real. Si pasa, queda listo para la ventana de release a main.
Validado
04

Manejo de Rediseños y Refactorizaciones

Un rediseño visual masivo (ej. migrar toda la UI a nuevos componentes) o un cambio arquitectónico profundo no puede bloquear el flujo continuo de entregas en staging ni los parches urgentes.

🔀

Feature Flags (Toggles)

Siempre que sea posible, el rediseño se mezcla continuamente a staging pero permanece **oculto bajo un flag** (ej. "UseNewDashboardV2": false). Esto evita la "fatiga de integración" (merge hell) y permite desplegar funcionalidades sin mostrar el trabajo incompleto.

🏗️

Ramas Epic (epic/redesign-v2)

Si el impacto rompe el modelo de datos o es imposible usar flags, se crea una rama epic/redesign-v2 desde staging. Esta rama se debe **rebasear contra staging** al menos una vez por semana para evitar que el código quede obsoleto.

05

Incidentes post-lanzamiento (Flujo Hotfix)

Cuando un bug severo llega a producción (el producto ya fue lanzado y el cliente detecta un fallo crítico), el flujo normal se interrumpe. La prioridad es restablecer el servicio en NxFortress o para el cliente final inmediatamente.

1
Crear rama desde main
No crees la rama desde staging. Ejecuta: git checkout main y luego git checkout -b hotfix/NX-999-auth-crash.
Crítico
2
Reparar y testear localmente
Implementa la corrección mínima y necesaria. Un hotfix no es lugar para refactorizar código estético, solo para apagar el incendio y restaurar operatividad. Escribe o arregla el test unitario asociado.
3
PR directo a main y despliegue rápido
Crea el PR directo hacia main. Requiere aprobación urgente del TL. Una vez mergeado, el pipeline CI/CD lanza a producción.
4
Sincronización (Backmerge a staging)
Inmediatamente después de mergear en main, debes llevar ese mismo cambio a staging para evitar que la próxima feature en desarrollo elimine tu parche.
Git
5
Post-mortem y Knowledge Base (KB)
El incidente termina documentando qué pasó y por qué en 11-incidents/ (BUG-XXX / INC-XXX). Si es un error operativo, se genera un Runbook y se guarda en docs/ asegurando el estándar de calidad y prevención a futuro.
ISO 9001
